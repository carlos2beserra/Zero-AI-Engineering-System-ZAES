# MAES v1.1.4

**Data:** 2026-06-05
**Tipo:** patch — correções e adições na documentação web (Fumadocs). **Sem mudança de comportamento do CLI nem do framework.**

## 🐛 Correções

### Comando CLI fantasma `maes eval` removido da documentação

A documentação descrevia um comando `maes eval` que **não existe** no core CLI. Na
realidade há dois mecanismos de eval, distintos:

- **Agent `/maes-eval`** — avaliação por cenários (`*.eval.yaml`), padrão WITH/WITHOUT/judge,
  delta de qualidade. Roda no LLM do próprio cliente, **sem API key**.
- **CI `eval-pr.py`** (workflow `maes-eval.yml`) — pontua o diff de um PR contra o rubric
  de `eval-rules.md` (score 0–14). **Requer API key**, sempre advisory.

As ~40 referências ao comando inexistente, em 12 páginas, foram corrigidas para apontar
para o mecanismo real.

### Schema de cenário de eval corrigido

A doc usava `expected_behavior`/`context_file`, que não existem. Alinhado ao schema real
(`expected`/`anti_expected`/`judge_prompt`) — o mesmo que `maes init` gera e que o agent
`/maes-eval` lê.

### Dois mecanismos de eval separados

A doc conflava o eval por cenários com o eval de PR em CI. Agora estão explicitamente
distintos em `reference/prompts.mdx` e na página do agent, com tabela comparativa.

### Acoplamento fictício "TASK = cenário de eval" desfeito

Em `task-format.mdx` e `conventions.mdx`: task files alimentam `maes explain context --task`
e o eval de PR (`eval-pr.py --task`); cenários são arquivos `.eval.yaml` separados.

## 📝 Documentação

### Uso ad-hoc do `/maes-eval`

Documentado o uso por task em texto livre (ex.: `/maes-eval corrigir responsividade da tela
de pipeline`), que faz o agent montar um cenário ad-hoc na hora. Marcado explicitamente como
**best-effort** — não faz parte do contrato formal do agent; para avaliação repetível,
escreva um `.eval.yaml`.

(`pyproject.toml`, `maes/__init__.py`): **1.1.3 → 1.1.4**.
