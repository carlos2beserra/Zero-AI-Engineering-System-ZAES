## ✨ Recursos

### Blueprint como Contrato Inicial de Engenharia (RFC 0001)

O Blueprint deixa de ser um catálogo de aplicações homologadas e passa a ser o **contrato
inicial de engenharia** de um projeto novo. O valor não é geração de código — isso continua
com as ferramentas oficiais de cada ecossistema (*Official First*) — e sim a **transferência de
conhecimento arquitetural organizacional** para o projeto no nascimento, de modo que uma IA
sustente os padrões da organização ao longo do ciclo de vida usando só o conhecimento que passou
a pertencer ao projeto.

O problema que isso resolve: após a criação, a IA tem stack e bootstrap, mas perde o que sustenta
o padrão — convenções, boundaries, *intended placement*, nomenclatura, decisões e padrões de
teste. Esse conhecimento só existia no fluxo brownfield (inferido pelo Analyze); no greenfield não
era semeado, e a IA não sabia responder "onde crio um módulo Financeiro?" ou "quais boundaries
nunca quebrar?".

Formalizado em [RFC 0001](../rfc/0001-blueprint-como-contrato-inicial-de-engenharia.md), sustentado
por cinco ADRs novas:

| ADR | Decisão |
| --- | --- |
| [0003](../adr/0003-context-ownership-principle.md) | **Context Ownership Principle** — o contexto semeado passa a pertencer ao projeto |
| [0004](../adr/0004-observed-vs-intended-placement.md) | **Observed × Intended Placement** + Divergence Visibility Policy |
| [0005](../adr/0005-autoridade-normativa-observacional.md) | **Autoridade normativa × observacional** — substitui "humano vence" |
| [0006](../adr/0006-upgrade-de-contrato-blueprint.md) | **Upgrade de contrato** + proveniência do seed |
| [0007](../adr/0007-enforcement-ownership.md) | **Enforcement Ownership** — "the Compiler is not an architect" |

### Catálogo com 4 Blueprints homologados

`maes blueprint list` passa a oferecer quatro aplicações, cada uma por engenharia reversa curada
de um projeto real:

- **`fastapi-api`** — FastAPI / Python / Uvicorn, SQLModel / Pydantic v2 / Alembic, PostgreSQL /
  JWT / RBAC, pytest / httpx / uv
- **`nestjs-api`** — NestJS / TypeScript, Prisma / PostgreSQL, Zod / Jest, Docker / pnpm
- **`nextjs-web`** — Next.js (App Router) / React / TypeScript, TanStack Query / Zustand,
  React Hook Form / Zod, shadcn/ui (Radix) / Tailwind, next-intl / pnpm
- **`react-spa`** — React / TypeScript / Vite, Tailwind / shadcn/ui, React Router /
  TanStack Query / Zod, Vitest / Docker / pnpm

Os padrões agnósticos levantados no `nextjs-web` foram replicados no `react-spa`, e o teste de
`blueprint list` passa a exigir os quatro — o catálogo não pode encolher sem quebrar a suíte.

### Instalação corporativa via `pip install maes[all]`

Distribuição oficial como pacote Python via **AWS CodeArtifact** (formato PyPI privado) — o MAES
passa a ser instalável sem clonar o repositório. Fluxo: `aws sso login` →
`aws codeartifact login --tool pip …` → `pip install maes[all]`. Documentado no README e em
[RELEASING.md](../RELEASING.md).

Acompanham: flag global `maes --version`, pipeline de release (`release.yml`) disparado por tag
`v*` com jobs encadeados `build → validate → publish` (guard de versão, build reproduzível em
Python 3.11, instalação do wheel em ambiente limpo + smoke, publicação via OIDC sem access key
fixa), `build-check` em todo PR, e testes de empacotamento validando o conteúdo real do wheel e
do sdist.

## 🐛 Correções

### Analyze: o mapa de arquitetura encolhia conforme o projeto crescia

Rodar `maes build-arch-map` duas vezes no mesmo repositório produzia um mapa **menor** na segunda
rodada — 49 → 22 nós — depois de o time adicionar código e documentação. Investigação completa em
[findings-discovery-sampling-e-placement-confidence.md](../development/findings-discovery-sampling-e-placement-confidence.md);
decisão de política em [ADR 0009](../adr/0009-observacao-exige-populacao-conhecida.md).

Seis causas-raiz independentes, todas no framework:

**`.tsx`, `.jsx`, `.vue` e `.svelte` eram invisíveis ao Stage 1.** As extensões não constavam em
`_SOURCE_EXTENSIONS`, e como o BFS de fontes e a detecção de entidades filtram por esse conjunto,
um projeto React/Next não tinha **nenhum** arquivo elegível fora de `_PRIORITY_FILES`. "Zero nós de
frontend" era um filtro, não orçamento esgotado — o Stage 2 já sabia processar essas extensões, e as
duas listas haviam divergido em silêncio. Agora existe um único `CANONICAL_SOURCE_EXTENSIONS`.

**Cobertura auto-referente.** `files_total` vinha da própria amostra truncada em 200k chars, então a
métrica era estruturalmente incapaz de revelar sub-amostragem: reportava 60,5% sobre 43 arquivos num
projeto de 848. O denominador passa a ser a população real.

**`_PRIORITY_FILES` só era resolvido na raiz.** Em workspace multirepo nenhum `package.json` era
encontrado e `is_frontend_project` saía `false` por ausência de evidência. Manifestos passam a ser
coletados em subprojetos (profundidade ≤ 2), ordenados por prioridade de tipo de manifesto — cortar
alfabeticamente encheria as vagas com `packages/` auxiliares enquanto o manifesto da aplicação nunca
seria lido — e `_detect_frontend_framework` casa por **basename**.

**`_collect_auth_models` coletava de diretórios ignorados.** Ao contrário dos demais coletores, não
chamava `_in_ignored`: `.venv/**/models/user.py` entrava como modelo de domínio do projeto.

**A reserva de 40% do orçamento para código não era garantida.** A coleta de auth/domain models era
isenta do cap da fase de prioridade e podia consumir até ~480k chars (40 arquivos × 12k), zerando o
BFS de fontes. O `_Collector` ganha soft limit e a fase inteira respeita os 60%.

**Ordenação dependente do SO.** A enumeração ordenava objetos `Path`, cuja comparação no Windows é
case-insensitive — a mesma árvore produzia ordens diferentes entre plataformas e, como o orçamento
corta a coleta no meio, **a ordem decide quais arquivos são lidos**. Passa a ordenar strings
relativas-posix.

### Observed Placement afirmava convenção sem lastro

`_dominant_prefix` somava cada nó também no prefixo de 1 segmento, então quando todos compartilhavam
a raiz o resultado era 100% → confiança `high` → renderizado **sem aviso** no `CLAUDE.md`. Em campo
saiu `Service → <raiz do repositório> (100%)`, orientando onde colocar código novo.

Três regras corrigem: prefixo de 1 segmento nunca é `high`; prefixo que não discrimina — ancestral
comum de todos os nós, quando há mais de uma categoria — é descartado por teste **estrutural**, nunca
por nome de diretório; e existe status próprio `no_observed_convention`, porque ausência de convenção
observável não é falta de dados.

## 🔧 Mudanças

### `architecture_map.json`: schema 2.0 → 2.1

A semântica das métricas de cobertura muda (o denominador passa a ser a população) e duas chaves do
funil são renomeadas: `discovered_files` → `source_files` e `total_nodes` → `node_count`.
"Discovered" era lido como "o que o collector achou", precisamente a interpretação que produziu o bug
do denominador.

Campos novos, todos observáveis:

- `sampling_ratio` e `sampled_files` — evidência × população, medidas em **quantidade de entidades**,
  não em volume de texto. Dois projetos de 100 arquivos, um com 20 linhas e outro com 3.000, têm o
  mesmo `sampling_ratio`; isso é intencional.
- `files_sampled` por nó — junto de `file_count` forma o par população/evidência. `files_sampled: 0`
  significa que **todo** campo semântico daquele nó está sem evidência, não que esteja vazio.
- **Structural Transformation Funnel** — `source_files → candidate_count → collapsed_count →
  node_count`. Descritivo, nunca avaliativo. `candidate_count` é a métrica sentinela: depende só do
  inventário e das regras de agrupamento, então variação sem mudança no projeto indica alteração da
  interpretação estrutural.
- `project_roots_discovered` / `analyzed` / `truncated` — um limite de proteção não pode parecer
  ausência de evidência. Regra de leitura: `is_frontend_project: false` com
  `project_roots_truncated: true` **não é evidência negativa**.

### `placement-map.json`: schema 1.0 → 1.1, com refusal-to-emit

Status distintos por causa: `generated`, `no_observed_convention`, `stale_schema`,
`invalid_artifact`, `unsupported_schema` e `empty`. Versão desconhecida nunca degrada em silêncio.

A evidência exigida depende do **tipo** de afirmação, e as duas políticas vivem em
`sampling_policy.py`, separadas do mecanismo de emissão:

| Afirmação | Exemplo | Evidência |
| --- | --- | --- |
| Derivada de **estrutura** | "onde vive um Service?" | topologia sobre a população (`schema_version`) |
| Derivada de **conteúdo** | `entry_points`, `dep_edges` | `sampling_ratio` |

Quando a evidência falta, a seção `## Code Placement` é **omitida** dos adapters e o `sync` explica
o motivo — omissão silenciosa lê como bug.

### Uma única enumeração da população

`scan_project()` passa a ser a fonte única de verdade para enumeração estrutural, consumida por todos
os coletores do Stage 1 — antes havia dois `rglob` completos mais 36 globs recursivos. Contrato:
rel-posix normalizado, ordem determinística, sem duplicatas, símlinks fora, nenhuma classificação
arquitetural, e estabilidade sobre caminho e existência apenas (metadado de filesystem nunca
influencia).

### `build-arch-map` não coleta mais documentação

`skip_existing_docs=True`: docs não contribuem para topologia e competiam pelo orçamento de conteúdo
de um mapa zero-LLM.

### `maes upgrade` ganha guardas de versão

Concordância entre a cópia vendorizada e o CLI instalado — o modo de falha mais difícil de
diagnosticar é o upgrade terminar **verde** enquanto o código que roda continua sendo o antigo. E
mensagem de fechamento apontando o próximo passo quando o architecture map está em schema anterior.

### `pyproject.toml` com versão dinâmica

Versão derivada de `maes/__init__.py` (fonte única), `include-package-data`, metadata completa e
`LICENSE` proprietário. O launcher legado `maes.py` foi removido — o módulo top-level sombreava o
package `maes/` e quebrava `python -m build`.

## ⬆️ Atualização

O fluxo oficial absorve a mudança sem intervenção manual:

```bash
maes upgrade          # a seção Code Placement fica OMITIDA — estado seguro
maes build-arch-map   # regenera o mapa em schema 2.1
maes sync             # Code Placement volta, agora com lastro
```

Após `maes upgrade`, o `sync` interno lê um mapa em schema anterior; pelo fail-closed a seção é
omitida em vez de reemitida errada, e o comando informa o próximo passo. `maes doctor` sinaliza schema
desatualizado. **Nenhuma migração é necessária** — `context/inferred/` e `synthesis/` são integralmente
regenerados.

Validado em campo num workspace multirepo de 941 arquivos de fonte:

| Sinal | Antes | Depois |
| --- | --- | --- |
| Nós | 22 | 151 |
| `source_files` (denominador) | 43 (a amostra) | 941 (população) |
| Nós de frontend | 0 | 18 |
| `is_frontend_project` | `false` | `true` |
| Code Placement | `Service → <raiz do repo>` 100% `high` | 5 entradas; a da raiz rebaixada a 73% `low` com ⚠️ |
